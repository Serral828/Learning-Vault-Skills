# Assess

评估的目标是获得有区分度的能力证据，而不是迫使用户复述刚讲过的内容。

## 评估前

1. 明确要观察的能力以及评估结果会怎样影响讲解重点、缺口记录和笔记内容。
2. 读取当前对话、`.learning/learner-profile.json` 和已有掌握证据。用户已经展示过的能力直接计入，不重复考察。
3. 估计用户当前边界，在边界稍外侧出题。若用户已掌握基本方法，转向约束冲突、失败归因、边界条件或实验设计。
4. 如果没有一个问题会改变判断，就不要为了流程而提问。

当本 Skill 由 `teach` 在学习节点边界调用时，第 4 条不代表可以跳过证据：

- 当前对话已经包含等价的新情境应用时，直接评价该回答并明确记录为节点证据，不重复提问。
- 只有复述、教师示例或“我懂了”而没有用户应用时，仍需给出一个新情境任务。
- 既没有必要提问也没有可评价证据，说明该内容不应是独立学习节点；返回 `teach` 合并节点，而不是把它静默标成完成。

## 学习节点检查点

`teach` 为每个规划节点提供节点名称、可观察完成标准和要求的证据等级。本 Skill 在节点教学和实例结束后单独执行一次检查点；一次调用只判定一个节点，并生成该节点自己的证据记录：

1. 优先判断用户在自然对话中是否已经完成了符合门槛的任务。
2. 缺少证据时只提出一个能够改变节点状态的核心任务。
3. 按目标等级把节点记为 `validated` 或 `assessed_with_gaps`。两种状态都表示本节点的一次评估已经完成，可以进入下一节点；后者必须记录具体缺口，但不得自动安排补测。
4. 同时检查是否已有用户自己的机制解释和新情境应用。两者齐备可提高证据等级；缺少时如实记录，不把笔记生成误当成用户已经掌握。

一个任务若覆盖多个紧密相关节点，必须分别说明每个节点获得的证据和状态。无法分别判断时，只能把它们视为一个合并节点。

## 综合评估

所有必需节点分别完成一次评估，并且用户已经完成实际应用输出后，由 `teach` 再调用本 Skill 一次并指定 `mode: comprehensive`。这次评估记录整个 Quest 的掌握程度，并确定 Distill 时哪些内容需要与掌握缺口分开处理：

1. 读取 Quest 完成标准、全部节点证据和用户的实际应用输出。
2. 检查输出是否联合使用必要节点、产生可观察结果，并体现关键决策或因果，而不是把零散练习粘在一起。
3. 优先直接评价真实输出；若成果没有暴露某项关键推理，可以在这次评估中提出一个整合性的变化条件、故障诊断或方案辩护任务，但不得在反馈后再安排第二轮补测。
4. 分别指出每个节点在成果中得到的证据，并给出 Quest 整体的 `passed` 或 `completed_with_gaps`。关键缺口必须明确列出，不能用平均分掩盖。
5. 综合评估完成后输出 `distillReady: true`，列出可准确整理的候选核心命题，并把尚未掌握的内容单独列为 gaps；Concept Note 的生成不等于把 gaps 标记为已掌握。
6. `completed_with_gaps` 不触发自动补教、修改输出或复评。用户以后明确要求巩固时，交给 `review` 或新一轮 `teach`，不作为本次 Distill 的前置条件。

综合评估是对实际应用的再次验证，不是 Agent 对前面节点评分的文字总结，也不是让用户确认“总结看起来对不对”。

## 问题准入门槛

提出前确认问题同时满足：

- **目标相关**：答案直接证明目标能力，而不是外围记忆。
- **不可复述过关**：仅把上一段换一种说法不能得到满分。
- **包含新情境**：加入真实案例、数据、约束、异常、反例或取舍。
- **有可观察标准**：能从回答中判断推理、适用条件或行动方案是否成立。
- **难度匹配**：不是用户已经明确展示过的常识，也不依赖尚未教授的隐藏前置。

任一项不满足就重写或取消问题。

## 优先任务类型

根据能力目标选择一种最合适的形式，不为凑数量全部使用：

- **预测**：条件改变后会发生什么，为什么。
- **诊断**：从日志、现象或结果定位最可能的失败机制。
- **权衡**：指标冲突时作出决定并说明红线。
- **设计**：设计实验、控制策略、评估方案或实现步骤。
- **迁移**：把概念应用到表面不同但结构相似的新问题。
- **反例与边界**：找出方案失效的条件并提出修正。

优先使用用户正在做的项目和真实目标作为背景。无法取得真实材料时，构造最小但完整的工程情境。

## 交互与语气

- 使用共同解决问题的专业语气，不扮演审讯者或故意装傻。
- 禁止使用“凭什么”“你怎么证明”“这不是显然吗”“连这个都”等贬低或挑衅表达。
- 不问答案显然包含在问题里的反问，不用“为什么需要指标”之类常识题拖延进度。
- 一次给足做判断所需的信息，然后只问一个核心任务。
- 回答充分时立即停止，不通过不断追加“那又怎样”制造虚假深度。

## 评价回答

先判断证据，再决定是否追问：

- `0 无证据`：没有作答，或内容与目标无关。
- `1 识别`：能复述或识别概念，但不能独立用于情境。
- `2 应用`：能在给定情境中正确运用，并说明关键理由。
- `3 迁移`：能处理新约束、边界或指标冲突，主动检查失败模式。

反馈时：

1. 先指出回答已经证明的能力。
2. 再指出影响结论的具体缺口；不要评价人格或笼统说“理解不够”。
3. 达到目标要求就结束评估。节点检查通常达到 `2` 记为 `validated`；未达到则记为 `assessed_with_gaps`，同样结束本节点并继续流程。
4. 未达到时只给出针对具体缺口的简短纠正或建议，不再换题补测，也不要求用户当场重新回答。只有用户明确要求重新练习时，才另行进入 `review` 或新的教学节点。

## 示例质量

低质量：询问“有了 eval set 和指标后你会怎么判断 Prompt 变好还是变坏”。这只诱导复述方法名。

合格：给出 Prompt A/B 在常规任务、边界安全、成本上的冲突数据，要求决定是否发布，并说明指标优先级、红线和下一项实验。该任务能够区分会背术语与会做评估决策。

## 输出证据

节点评估结束后简要记录：`mode: node`、节点名称、目标能力、任务情境、要求等级、实际证据等级、节点状态、已证明内容、剩余缺口和下一步。节点状态只表示掌握证据，不单独决定 Distill。

综合评估结束后记录：`mode: comprehensive`、实际应用输出、Quest 完成标准、整体状态、各节点在成果中的证据、跨节点决策、剩余缺口、候选核心命题和 `distillReady: true`。把结果返回 `teach`；只有需要持久化时才提议写入 Session Log 或掌握状态，未经用户确认不修改正式笔记。
