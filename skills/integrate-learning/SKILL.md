# Integrate Learning

把用户已经理解并亲自记录的材料纳入正式知识网络。输入笔记是本次转换的唯一内容依据，但不是外部事实的证据来源；视频、课程、书籍、实践或个人推断才是可选的溯源信息。

本 Skill 使用封闭语料转换：开始前必须读取并遵循 [原始笔记的封闭语料转换边界](../../docs/raw-note-conversion-boundary.md)。转换只忠实处理本批次原始笔记，不承担补课或扩写；任何原文之外的建议、延伸或质疑只能在转换完成后的独立报告中提出。

## 1. 接收并约束输入

要求用户给出 Vault 相对路径，例如：

```text
/skill:integrate-learning 00-原始笔记/高速PCB.md
/skill:integrate-learning 00-原始笔记/STM32/
```

执行前必须：

1. 解析 Vault 根目录和用户给出的路径。
2. 拒绝绝对路径、包含 `..` 的路径、符号链接跳转以及不在 `00-原始笔记/` 下的目标。
3. 单文件目标必须是 `.md`；目录目标递归收集 `.md` 文件。
4. 按 Vault 相对路径排序，并在开始时冻结为“输入清单”。之后新出现的文件不自动加入本批次。
5. 非 Markdown 文件不作为独立输入读取、计入覆盖率、移动或删除；但 Markdown 中的图片嵌入及其紧邻说明必须按下述图片约定扫描，不能因为图片文件不是 Markdown 就忽略这部分语义。

目标不存在、没有 Markdown 文件或安全边界无法确认时停止并说明原因。不要退化为扫描整个 `00-原始笔记/`。

## 1.1 图片—说明对预检

拆分内容前必须读取并遵循 [原始笔记图片说明约定](../../docs/raw-note-images.md)。本批次每张 Markdown 图片、Obsidian 图片嵌入或 HTML 图片的下一物理行，都必须是一整行由英文括号 `(...)` 或中文括号 `（...）` 包围的内容说明；图片和说明之间不能有空行。

Agent 不依赖直接识图，只依据括号中的用户说明判断图片表达的对象、关键元素、关系、数值、现象和用途。例如：

```markdown
![[附件/KNN决策边界.png]]
（二维分类图：K=1 时决策边界曲折，K=15 时更平滑，用于说明较小的 K 更容易受噪声影响。）
```

装饰图片也要写明 `（装饰性图片，不承载知识内容。）`。图片与说明是不可拆分的内容单元：说明行只归属于上一张图片，不作为普通正文再次切分，但其中的知识参与后续语义分析和去向规划；只要该单元被晋升到正式笔记，就必须连同图片和说明一起写入。

如果下一行缺失、是空行、括号不成对、括号内容为空，或只有“见图”“示意图”等不足以理解图片的文字：

1. 一次性列出所有问题的笔记相对路径、图片行号、图片目标和原因；
2. 提醒用户在每张图片下一行补充合格说明；
3. 将图片及依赖它的内容单元标记为 `未处理 → 缺少可用图片说明`；
4. 可以继续分析不依赖这些图片的正文，但不得提交声称 100% 覆盖的最终计划、不得晋升依赖图片的知识，也不得进入清理；
5. 不根据文件名、alt 文本、上下文或常识猜测图片内容。用户补充后重新扫描本批次。

## 1.2 表格结构预检

拆分内容前必须读取并遵循 [原始笔记表格保真规范](../../docs/raw-note-tables.md)。扫描 Markdown 与 HTML 表格，为每张表分配批次内 Table ID，记录原文件、起止行、表头、行标识、列数以及结构状态。

表格的表头、行列对应、顺序、空值状态和单元格归属都属于知识，不是可以随意丢弃的排版。对比、映射、规格、参数、决策、条件—结果和数据型表格默认继续使用 Obsidian 可解析的 Markdown 表格；不得只保留单元格文字，再摊平成连续正文或无对应关系的列表。

表格边界含混、表头与数据列无法对应、合并单元格语义不明或空值含义无法判断时：

1. 一次性列出 Table ID、相对路径、行号和具体问题；
2. 标记为 `未处理 → 表格结构含混`，提醒用户修复或确认；
3. 可以继续分析不依赖该表的内容，但不能把表格计入 100% 覆盖、不能写入依赖它的正式知识，也不能进入输入清理；
4. 不根据上下文或常识猜测缺失的表头、行标识、单元格边界或值。

## 2. 切分内容单元

逐篇读取冻结清单，将内容穷尽地切分为可追踪的原子知识点，并为每项分配批次内 ID、记录原文件和行号。除了概念段落，还必须保留条件、限制、数值、例子、反例、疑问和不确定判断，不能用摘要替代细节。原子知识点例如：

- 一个边界清楚的概念或因果命题；
- 一套方法、流程、规则或检查项；
- 一个需要连接到 Topic Map 的主题入口；
- 输入中明确写出的来源信息；
- 用户的例子、推导、观察、疑问或尚不可靠的判断。
- 图片下一行括号说明中表达的结构、数值、现象、结论或案例；它与对应图片作为一个内容单元处理。
- 表格整体的表头、行列关系和顺序，以及每个具有知识含义的单元格；单元格账本项必须记录 Table ID、行标识和列表头，不能脱离行列语境切成普通句子。

切分是为了追踪去向，不是为了机械地“一段生成一篇笔记”。保留原意、适用条件、反例与用户尚未解决的不确定性；不得替用户补造事实、来源或理解证据。

建立覆盖账本，记录每个知识点的唯一预定结果和最终结果。重复知识可以合并到同一目标，但每个原始位置仍要在账本中指向合并后的段落。疑似错误、冲突或不完整内容按“原始笔记观点 / 待核查”保留，不能因为 Agent 不认同就省略或静默改正。

## 3. 检索正式知识并决定去向

制定去向前读取并遵循 [标签注册表](../../docs/domain-tags.md)。为 Concept Note、来源和实践等非结构节点选择一个主领域，真正跨领域时最多两个；Learning Quest 统一只使用 `quest`，Topic Map 统一只使用 `map`。细粒度主题保留在 `topics`、Topic Map 或正文链接中。

创建或更新 Concept Note、方法或实践笔记时，同时读取并遵循 [正式笔记的实例与链接规范](../../docs/concept-note-writing.md)。Concept Note 使用 [默认模板](../distill/assets/concept-note-template.md)，但不得为了满足模板或案例规范补造原始笔记没有的知识材料。只有原始笔记已经提供应用案例时才能写入案例；材料不足时完整保留已有内容并标记为待补充或不晋升，在转换外建议中说明缺口。

对 `02-概念/` 做查重和关系候选审计时，区分“知识正文”和“关系边”：知识正文仍只能来自本批次输入；关系边可以由本批次输入与已有正式笔记共同提供双侧证据。只有两侧通过同一个具体机制、计算对象、输入输出或依赖条件直接衔接，而且无需补造中间知识时，才能提出正式关系。不得把已有笔记正文复制进新笔记正文，也不得仅凭标题、关键词、标签或同处一张 Topic Map 建立关系。

每条双侧证据关系必须建立关系证据账本，记录：本批次原始片段及位置、已有正式笔记片段及位置、共同机制或对象、一句话桥接理由、关系类型，以及新旧两侧准备写入的最小 Wikilink。任一侧没有明确证据或桥接依赖未记录知识时，只能进入转换外建议。

只检索正式知识目录与必要的本地状态，不把默认隔离目录当作搜索语料：

- `01-学习问题/`
- `02-概念/`
- `03-主题地图/`
- `04-来源/`
- `05-实践与产出/`
- 必要时 `90-学习会话/`、`99-归档/` 和 `.learning/`

为每个内容单元选择恰当去向：

- 概念、机制、边界清楚的命题：新建或更新 `02-概念/`。
- 主题入口与多笔记导航：新建或更新 `03-主题地图/`。
- 方法、流程、检查清单、设计步骤或实践总结：新建或更新 `05-实践与产出/`。
- 只有输入明确包含标题、作者、链接、课程或出版信息等出处时，才新建或更新 `04-来源/`。
- 暂时不宜正式化但值得保存的内容：明确保留到某个精确位置。
- 重复内容：合并到同一目标段落，但覆盖账本仍分别记录每个原始知识点的去向。
- 疑似错误、内部冲突、证据不足或尚不完整的内容：忠实保留并标记为待核查，不擅自修正，也不作为自动丢弃理由。
- 纯排版残留、无知识含义的噪声或用户明确要求不保留的内容：只能在计划中展示原始位置和理由，并由用户接受后标记为“明确丢弃”。

先查重再决定新建。不要用同义标题制造重复 Concept Note；也不要把“高速 PCB”“STM32”这类宽主题整体塞进单篇概念笔记。

## 4. 提交一次批次整合计划

写入前向用户展示一份可核查的完整计划，至少包含：

- 冻结的输入清单；
- 图片—说明对清单，包括每张图片的目标、说明摘要和 `有效`、`装饰`、`缺失` 或 `说明不足` 状态；准备晋升的图片还要列出目标正式笔记、插入章节、最终可解析的图片链接和最终括号说明；
- 表格清单，包括 Table ID、原文件与行号、表头和行标识摘要、结构状态、`原样保留`/`格式修复`/`拆分`/`合并`/`转置`/`转为其他结构`、目标文件与章节，以及最终 Markdown 预览；非原样保留时还要展示理由和原表到目标结构的完整行列映射；
- 覆盖账本：每个原子知识点的 ID、原文件与行号、内容摘要和预定去向；合并项也必须指向具体目标段落；
- 准备新建的文件及其核心命题或用途；
- 准备更新的文件及差异摘要；
- 每条双侧证据关系的原始片段、已有笔记片段、共同机制、桥接理由、关系类型和两侧最小修改；
- 每个新建或更新文件拟使用的标签；Learning Quest 明确列为 `quest`，Topic Map 明确列为 `map`，其他正式知识列出领域标签；
- 每篇解释型笔记拟加入的领域应用案例、使用的实际材料、作用和验证状态；
- 拟建立的 Obsidian Wikilink、关系类型和理由；
- 因新知识而需要补充反向关系的已有 Concept Note、每篇旧笔记的最小差异；没有可成立关系时列出检查范围和不建立关系的原因；
- 保持不变的相关文件及理由；
- 每个内容单元的预定状态与去向；
- 明确丢弃项及理由；
- 无法处理或需要用户决定的项。
- 计划中准备写入的每条实质性内容如何追溯到原始知识点；任何无法追溯的新增内容必须在确认前删除，而不是请用户批准其混入本批次。

如果非 Learning Quest、非 Topic Map 内容不适合注册表中的任何领域，在计划中提议新的宽泛标签，说明边界和理由，并把注册表变更纳入同一次批次确认。不得使用 `domain/other`，也不得按单个技术或笔记临时造窄标签。Learning Quest 和 Topic Map 不触发领域标签扩展。

最后只请求一次批次确认。用户回复“可以”“继续”“按这个做”等普通肯定答复，即授权计划中列出的全部非破坏性创建和更新，不再逐文件追问。

用户没有确认前不写正式知识。实际执行需要新增、改名、覆盖或改变计划中的目标时，先暂停并展示偏差，获得新的批次确认。

## 5. 精确写入

严格按已批准计划执行：

- 更新前重新读取目标，防止覆盖用户在确认后作出的修改。
- 只写入覆盖账本中可追溯到本批次输入的实质性知识。允许结构化改写、去重和必要过渡语，不得增加输入之外的定义、机制、因果、例子、代码、公式、参数、数值、应用或结论。
- 保留现有 YAML、标题、链接、无关标签和有价值内容；更新项不得整篇静默重写。
- YAML 的 `tags` 使用列表格式；非 Learning Quest、非 Topic Map 的正式知识文件包含一个主领域标签，真正跨领域时最多两个。
- Learning Quest 的 `tags` 固定为只包含 `quest`；更新现有 Quest 时移除 `domain/...` 和其他细分标签，保留与标签规则无关的 YAML 字段。
- Topic Map 的 `tags` 固定为只包含 `map`；更新现有 Topic Map 时移除其中的 `domain/...`，保留与标签规则无关的 YAML 字段。
- Concept Note 写明输入已经支持的唯一核心命题，再用输入现有材料连贯组织定义、组成和机制。原始笔记已有领域应用案例时，将其嵌入所解释的步骤，并在不新增事实的前提下抽象原文已经支持的一般规律；原始笔记没有案例、代码、工程参数或其他材料时不得生成。已有代码块仍须添加知识解释性注释，但注释只能解释原始代码与原文已经表达的机制，不能借注释补入新知识。
- 原始笔记中的图片—说明对只要被用于正式知识，就在它实际解释的机制、步骤或案例附近整体写入：图片嵌入后下一物理行立即写完整的 `(...)` 或 `（...）` 说明，中间不得有空行。不得只复制说明、只保留图片或把两者拆到不同章节；附件路径无法稳定解析时保持该单元未处理。
- 原始笔记中的语义表格默认以 Markdown 表格保留。写入时保留表头、行标识、具有语义的行列顺序、每个单元格的行列归属、空值状态、单位、链接、代码和公式；不得把表格摊平成连续文字后声称内容完整。
- 只有 [表格保真规范](../../docs/raw-note-tables.md) 允许的无歧义格式修复可以直接执行。拆表、合表、转置、重排行列或把语义表格改成其他结构，必须已经在确认后的批次计划中展示理由、最终预览和完整映射；结构变更不能授权补写原表没有的值或结论。
- 不把输入笔记中的学习过程机械转成“我的理解”或“理解验证”。用户掌握证据属于状态或 Session Log；只有确有长期溯源价值时才增加“参考”章节。
- Concept Note 的关系使用 `[[目标笔记]]`，并同时写关系类型与理由；不得用纯文本笔记名代替链接。
- 新建或实质更新 Concept Note 时，检查它与已有概念之间是否存在前置、输入、机制组成、解释、实现与加速、应用、对比或一般化关系。关系可以由本批次输入单独明确表达，也可以由本批次输入和已有正式笔记通过共同机制提供双侧证据；后一种情况必须已在确认计划中展示关系证据账本。确认成立后同时更新新旧两侧；只改新笔记或依赖自动反向链接不算完成。缺少任一侧证据、需要补造中间知识，或只能依赖标题、标签与 Agent 常识时，不写入正式关系，只放入转换外建议。
- 若整合出的 Concept Note 与现有 `01-学习问题/` 有明确的实际目标关系，提议同时更新两侧：Concept Note 反向链接 Quest，Quest 的 `## 涉及概念` 链接 Concept Note。不得依据词语相似批量建立关系。
- Topic Map 负责导航，不复制各 Concept Note 的正文；导航目标使用实际 Wikilink。
- 新建或更新 Topic Map 时，按 [Topic Map 创建与归属规范](../../docs/topic-map-writing.md) 选择适合该主题的主组织轴。读取全部现有链接目标，将 Concept Note 放进有语义的分组并按依赖或领域自然顺序排列；新条目加入后必要时同步移动或重排旧条目，不能只追加到平铺清单。地图分类属于结构整理，但新条目的导航说明仍只能概括本批次输入已经支持的内容；不得借地图更新补写新知识，也不得重写旧条目的实质性说明来扩展本批次范围。
- 方法和检查清单保留顺序、判断条件、失败模式与实际约束。
- 来源记录只写输入中实际存在的溯源信息；缺少信息时标记缺失，不猜测。

## 6. 回读验证与覆盖报告

写完后重新读取所有新建或更新的目标，验证：

- 文件存在且内容可解析；
- 标题、核心命题和目标目录符合计划；
- Learning Quest 的标签恰好为 `quest`；Topic Map 的标签恰好为 `map`；其他正式知识的领域标签存在、属于已确认的注册表且数量不超过两个；
- 对已经晋升的解释型笔记，确认其原始输入本身包含足够的领域应用案例，并且整理后仍保留具体条件、实施材料、可观察结果、概念映射和条件变化；输入不具备这些材料的内容应保持待补充而不是被扩写晋升；
- 已由输入支持的 Concept Note 案例与机制阐述连贯，且不存在遗留占位符、空的“参考”章节、学习验收问题或 Agent 自行补出的内容；
- 关系和 Topic Map 目标使用可解析的 Obsidian Wikilink，而不是纯文本名称；
- Topic Map 中的 Concept Note 已按主题匹配的语义分组组织，组内顺序可解释，且不存在空分组、“其他”兜底或四个以上概念仍平铺的笼统清单；
- 每条确认成立的 Concept Note 关系都已在新旧两侧显式写入，且没有重复等价链接；
- 每条双侧证据关系都能回指本批次原始片段和已有正式笔记片段，桥接理由只表达两侧共同支持的直接联系；已有笔记内容没有被复制进本批次知识正文；
- 新增的内部链接能够解析，或被明确标记为待建链接；
- 没有覆盖计划外的内容；
- 每篇输入笔记及每个内容单元恰好具有一个最终状态。
- 每张图片都有合格的紧邻括号说明；缺失或说明不足的图片不存在于声称已完成的覆盖范围中。
- 每个晋升到正式笔记的图片—说明对都完整保留，图片与说明物理相邻、附件目标可以解析，且不存在有图无说明、有说明无图或同图无意义重复嵌入。
- 每张表都能被 Markdown/Obsidian 解析；表头、行标识、语义顺序、空值状态和每个非空单元格均有唯一目标，行列归属没有改变。拆分后的子表保留共同的行标识与上下文，不存在把表格压缩成无法恢复对应关系的正文。
- 输入到输出检查：覆盖账本中每个知识点都有唯一状态，所有条件、边界、数值、例子、反例、疑问和不确定性均有去向，没有被宽泛摘要吞掉。
- 输出到输入检查：正式输出中的每条实质性定义、机制、事实、例子、参数和结论都能指向一个或多个原始知识点；普通关系同样回指原始知识点，双侧证据关系则同时回指原始片段、已有正式笔记片段和桥接理由。没有来自模型常识、外部搜索或已有笔记正文的无来源正文扩写。

覆盖报告的状态只能是：

- `已整合 → <目标文件>`
- `已合并 → <目标文件#段落>`
- `已保留 → <精确位置>`
- `明确丢弃 → <用户已接受的理由>`
- `未处理 → <原因>`

按“已有最终状态的原子知识点数 / 原子知识点总数”计算覆盖率。只有没有任何 `未处理`、覆盖率为 100%，且输出到输入检查没有发现无来源扩写时，整合才完成。验证失败或存在未处理项时，保留输入原位并报告下一步，不得进入清理。

## 6.1 转换外建议

覆盖报告完成后，可以单独输出以下三类内容：

- `建议`：结构、验证或实践方式可以怎样改进；
- `延伸`：原始笔记之外、以后可能值得学习的相邻问题；
- `质疑与待核查`：原笔记中证据不足、互相冲突、含混或可能错误的内容。

本节必须明确标记“未写入正式笔记，不属于本批次转换内容，不计入覆盖率”。不要为了凑数量制造建议；没有可靠建议时可以省略某一类或整个部分。用户选择后，将其作为新的 `teach`、`verify` 或笔记更新任务处理，不能追写进已经确认的本批次输出。

## 7. 可恢复地清理输入

达到 100% 覆盖后，展示将移动的精确 Markdown 输入清单，并询问是否移入 `.trash/`。普通肯定答复即可授权这次可恢复移动。

移动规则：

1. 只移动冻结清单里的 Markdown 文件。
2. 保留 `00-原始笔记/` 下的相对路径。例如 `00-原始笔记/STM32/定时器/PWM.md` 移到 `.trash/00-原始笔记/STM32/定时器/PWM.md`。
3. 目标已存在时不覆盖，停止该批次清理并报告冲突。
4. 移动后只清理本批次路径中已经为空的目录；始终保留 `00-原始笔记/` 根目录。
5. 非 Markdown 文件会使目录保持非空，绝不随目录删除。
6. 移动 Markdown 前验证其中所有图片引用在新位置仍可解析；相对引用会失效、附件缺失或会产生孤立附件时停止清理并报告，不静默改写或移动图片。
7. 清理后再次核对原路径、回收路径、图片引用和输入清单，并报告结果。

本 Skill 永不永久删除输入，也不自动清空 `.trash/`。永久清空只能由 `/skill:purge-trash` 或用户明确的清空命令触发。
