# Distill

## 晋升门槛

正式 Concept Note 必须同时满足：

- 当前 Learning Quest 的全部必需节点已经分别完成一次节点评估，状态可以是 `validated` 或 `assessed_with_gaps`。
- 用户已经完成覆盖这些节点的实际应用输出，且一次综合评估已经结束，状态可以是 `passed` 或 `completed_with_gaps`。
- 用户自己的解释和新情境应用作为掌握证据记录；它们影响 mastery 状态，但不是生成一篇准确知识笔记的补测门槛。
- 关键事实有来源或被明确标注为个人推断。
- 笔记边界足够小，并有一个唯一核心命题。

如果教学流程尚未完成首次节点评估、实际应用输出或首次综合评估，保留在 `90-学习会话/`。评估已完成但存在缺口时可以继续 Distill，同时把缺口留在掌握状态中。

用户审阅或确认一篇流畅草稿，只能授权修改或写入，不能替代首次节点评估、实际应用输出或首次综合评估。这里要求的是每个阶段执行一次，不要求失败后补测或复评。

## 编排触发

- `teach` 只有在全部节点各评估一次、实际应用输出和一次综合评估依次完成后，才在收束审计中主动调用本 Skill；用户不需要再发一次 `/skill:distill`。
- 接收到综合评估 `passed` 或 `completed_with_gaps` 且 `distillReady: true` 的结果后，直接进入查重和草稿流程；不要再问用户“先补测还是先起草”。
- 即使某个节点的局部证据已经很强，也不能在 Quest 综合评估前提前整理。综合评估用于区分可写入的准确知识与仍需保存在 mastery 状态中的个人掌握缺口。
- 展示完整草稿并请求确认是 Distill 提案本身，不等于未经授权写文件。用户确认后才落盘。
- 用户明确没时间查看草稿时，将该节点交给 `learning-hub` 保存为待执行 `distill` 动作；下次恢复先展示草稿，不重新教授或补测已经评估的节点。
- 用户明确拒绝本次晋升时记录为 `declined`，不要在同一证据不变时反复推销；以后由用户主动要求或新增证据后再提议。

## 提炼流程

1. 搜索 `02-概念/`，避免创建重复或近义笔记。
2. 读取当前 Quest 各节点的 `clarificationInsights` 和 `deferredDependencies`，并通过 `defer-concept` 读取相关暂存摘要。列出每条实质性疑问最终讲清了什么，以及应进入笔记的哪个部分；暂存快照只用于识别禁止冒充掌握或扩写的边界，不是笔记素材。
3. 选择清晰的名词短语标题；Topic Map 才使用宽泛主题名。
4. 保留用户表达中准确、有辨识度的理解，并把疑问解答自然融入定义、直觉、机制、边界、误区、案例或关系；不要把对话原话单独堆成“我的理解”或问答记录。
   - 存在未解决的 `blocking` 暂存依赖时，当前节点不能进入 Distill；返回 `learning-hub` 保留待恢复动作。
   - 未解决的 `supporting` 暂存知识不妨碍主节点 Distill，但不得根据教学快照补写其机制、生成独立笔记或声称用户已掌握。只有暂存前已经准确讲清的关系事实确实属于主命题时，才可简短写明“相关但本次未展开”；没有真实 Concept Note 时不制造 Wikilink。
   - 暂存概念以后通过正式 Quest 完成正常评估、实际应用和综合流程后，才可能成为独立 Concept Note 候选。
5. 读取并遵循 [领域标签注册表](../../docs/domain-tags.md)，选择一个主领域；只有真正跨领域时才增加第二个标签。
6. 读取并遵循 [正式笔记的实例与链接规范](../../docs/concept-note-writing.md)，为当前概念选择与领域真实工作方式匹配的应用案例，并对 `02-概念/` 执行增量关系检索。除查重外，还要主动寻找“已有笔记依赖这个新概念”“新概念解释或支撑已有机制”“两者存在应用、对比或一般化关系”的旧 Concept Note；不能只检查新笔记准备链接谁，也要检查哪些旧笔记现在应当反向链接新笔记。
7. 读取并遵循 [Topic Map 创建与归属规范](../../docs/topic-map-writing.md)，为当前概念选择至少一个最直接的上位主题地图并搜索 `03-主题地图/`。地图存在时，读取其全部链接目标，根据地图的主组织轴确定新概念的语义分组，并检查旧条目是否需要移动、改组或重排；不得只向“已晋升的概念”清单末尾追加。地图不存在时必须准备一份带真实语义分组的最小地图草稿，不能检查后不了了之。
8. 以 [Concept Note 模板](assets/concept-note-template.md) 生成草稿，并删除所有说明性占位符。`## 关系` 必须是一级标题后的第一个二级章节，然后才是“核心命题”和知识正文；YAML 保持在一级标题之前。除非用户明确指定其他模板，不沿用旧模板中的“我的理解”“形式与例子”“理解验证”“来源与证据”等固定章节。
9. 按正式笔记规范执行强调审计：重要概念词汇的首次引入、命名、定义或最关键机制阐述使用 `==...==`；其他重要结论、因果判断、操作原则、适用边界或易错提醒使用 `**...**`。一句话同时符合两类时只用高亮，禁止嵌套；不得在 YAML、标题、代码围栏、终端输出或独立公式内部添加标记，也不得整段滥用强调。
10. 在“概念与机制”的相应位置嵌入至少一个领域匹配的实际应用案例，包含具体场景、目标、条件、实施材料、可观察结果、概念映射和条件变化。软件知识按需使用实际代码、查询、配置或日志；硬件知识使用具体器件参数、连接或布局约束、测量与故障诊断；其他领域使用相应的演算、实验、决策、文本或设计案例。案例后必须抽象回一般机制，不能形成与正文割裂的附录。草稿包含图片时，图片下一物理行必须紧跟 `(...)` 或 `（...）` 解释，图片和说明作为一个单元放在所解释的机制附近；不得有图无说明、只有说明没有图片或附件目标无法解析。
11. 草稿包含代码块时，逐块执行代码注释审计：组件职责、数据语义、阶段机制、关键参数理由、公式映射和结果边界中凡与该代码相关的内容，都要用紧邻代码的知识解释性注释呈现。不得生成只有代码、只有步骤编号或只有语法翻译的代码块；不得为加注释破坏 JSON 等严格格式的有效性。
12. 对每条 `clarificationInsights` 做覆盖检查：机制疑问进入正文解释，区别或限制进入边界与误区，新增实例进入相应机制段，关系疑问转成有理由的 Wikilink。再对 `deferredDependencies` 做排除检查：没有把未解决的暂存内容写成已经讲清、已经验证或用户已经掌握。只有明显与笔记核心命题无关的澄清才可不写，并在草稿说明中指出原因。
13. 对每个确认有直接语义关系的已有 Concept Note 准备成对更新：新笔记写一条指向旧笔记的关系，旧笔记也写一条指向新笔记的关系。两侧关系类型可以不同，但理由必须分别从各自视角说明同一联系。例如“数据表示与特征向量”可写“应用于：KNN”，已有“KNN”则写“前置：数据表示与特征向量”。只改新笔记、不改旧笔记，或只依赖 Obsidian 自动反向链接面板，都不算完成。
14. “关系”中的每个目标都使用实际 Obsidian Wikilink，并写明关系类型和理由；模板里的纯文本槽位不能原样保留。若旧笔记没有“关系”章节，则在一级标题后创建；若关系章节在文末或正文中部，则在差异中展示并把整个章节原样移动到一级标题后，再执行最小关系更新；若只有“暂无已验证关系”则替换它；已有等价关系时不重复追加。新 Concept Note 必须链接所选主 Topic Map，Topic Map 也必须链接该 Concept Note。不得制造无依据链接。
15. 读取当前 Quest 的 `questPath`，确认该 Quest 的 YAML `tags` 只包含 `quest`；在 Concept Note 的“关系”中加入 `解决问题：[[01-学习问题/<Quest 文件>|<Quest 标题>]] — <本概念如何帮助解决该问题>`；同时在 Quest 的 `## 涉及概念` 中加入 `[[02-概念/<Concept 文件>|<概念标题>]] — <它在该问题中的作用>`。两侧必须指向真实文件，不能只写一侧或只写 Quest ID。
16. 在同一次确认中分项展示 Concept Note 的目标路径、领域标签和完整草稿；每篇受影响的已有 Concept Note 的路径、关系类型、理由和最小差异；Learning Quest 的目标路径及“涉及概念”更新差异；Topic Map 的目标路径、主组织轴、新概念的目标分组与组内位置、旧条目的移动或重排摘要，以及完整新建草稿或更新后的最终结构。若检索后没有可成立的旧概念关系，明确说明检查范围和未建立关系的原因，不能静默跳过。若需要新增宽泛领域标签，把注册表变更也并入这次确认。
17. 用户确认关系更新后，把新 Concept Note、受影响的已有 Concept Note 和 Quest 各侧一起写入并回读，验证每一对 Wikilink 都双向存在且目标可解析。任一侧被推迟时，把具体文件对、两侧链接文本和理由作为 `link-knowledge` 动作交给 `learning-hub`，不得因新 Concept Note 已写入而丢失。
18. 用户可以分别确认 Concept Note、已有概念双向关系、Quest 双向链接和 Topic Map。确认后才写入对应文件并更新状态；关系或 Topic Map 变更被推迟时，把具体目标和待执行操作交给 `learning-hub` 保存。

## Topic Map 收尾门槛

每篇新晋升的 Concept Note 都必须完成一次地图路由：

- 对 KNN 这类小知识点，选择“机器学习”这类可持续扩展的上位知识面，而不是创建“KNN Topic Map”。
- 若合适地图已经存在，Distill 提议更新它；若不存在，Distill 必须提议创建它。
- “未找到 Topic Map”是创建提案的触发条件，不是允许结束的条件。
- 地图提案必须展示采用的组织轴、新概念所属分组、组内位置，以及受影响旧条目的移动或重排。已有四个以上概念仍平铺在“已晋升的概念”“从这里开始”等笼统清单时，必须在本次更新中提出分类重构。
- 分类标题由主题内容决定；不得机械复制“基础/进阶”或机器学习示例。空分组、虚假占位和长期“其他”分类都不允许。
- 新建或更新的 Topic Map 统一只使用 YAML 标签 `map`，不添加 `domain/...`。
- 用户明确拒绝地图变更时可以结束本次地图提案；用户只是没时间时必须保存为待完成动作。

## 已有 Concept Note 关联门槛

每篇新建或实质更新的 Concept Note 都必须完成一次增量关系审计。至少检索同一 Topic Map 的概念、当前 Quest 已链接的概念、正文或关系中出现相关术语的概念，以及可能把当前概念作为输入、前置或机制组成的已有概念。

- 找到直接关系时，必须展示并维护新旧两侧；Obsidian 自动显示的未写入反向链接不能代替旧笔记中的显式关系。
- 没有直接关系时可以不修改旧笔记，但必须报告已经检查以及为何没有建立关系。
- 仅仅同属一个领域、标签或 Topic Map 不足以建立关系；必须能说明一个概念如何依赖、解释、应用、对比或推广另一个概念。
- 用户明确拒绝某一关系时可以不写；用户只是推迟时必须保存 `link-knowledge` 待办，不能把关联审计标为完成。

不得直接覆盖已有 Concept Note。需要修改时先展示差异和理由，保留现有无关标签；增加、移除或替换领域标签必须出现在差异中。

`理解验证`、用户作答和晋升证据写入掌握状态或 Session Log，不进入 Concept Note。只有存在值得未来追溯的外部资料、标准、数据或实验记录时才增加“参考”，不为满足格式创建空章节，也不把本次对话当成来源。

展示草稿前自检：YAML 是否仍在最前、`## 关系` 是否是一级标题后的第一个二级章节；正文是否先完成基本阐述；重要概念的首次引入或关键机制句是否使用成对的 `==...==`；其他重要结论是否使用成对的 `**...**`；是否没有嵌套、跨段、代码内强调或大面积滥用；每条实质性疑问解答是否已经融入合适位置或明确说明不纳入原因；是否不存在未解决的阻塞依赖；辅助暂存知识是否被排除且没有被误生成独立笔记或标成已掌握；案例是否嵌入并推动机制解释；每个可执行代码块是否包含知识解释性注释，并说明相关组件、数据、机制、参数、结果和边界；代码是否仍保持有效、正确缩进且没有 Markdown 转义标识符；每张图片是否紧邻一段成对括号说明、附件可解析且图片与说明没有被拆开；是否使用该领域真实的应用材料；是否包含具体约束、过程、结果和条件变化；是否把构造案例冒充真实事件；关系目标是否写成可解析的 `[[...]]`；是否执行了已有 Concept Note 增量关系审计；每条成立的概念关系是否同时准备了新旧两侧差异；Concept Note 是否反向链接当前 Learning Quest；Quest 的“涉及概念”是否链接该 Concept Note；两侧是否分别说明关系理由；Quest 标签是否恰好只有 `quest`；是否已经为新概念选择上位 Topic Map；地图是否声明或体现了适合本主题的组织轴；每个概念是否进入有语义的分组并按依赖或领域顺序排列；更新旧地图时是否检查了全部已有条目并展示必要的移动或重排；地图不存在时是否展示了创建草稿；Concept Note 与地图是否双向链接；地图标签是否只有 `map`。
