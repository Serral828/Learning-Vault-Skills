# Distill

## 晋升门槛

正式 Concept Note 必须同时满足：

- 用户已经用自己的语言解释核心机制。
- 至少完成一次新情境中的判断、推导或应用。
- 关键事实有来源或被明确标注为个人推断。
- 笔记边界足够小，并有一个唯一核心命题。

如果不满足，保留在 `90-学习会话/`，不要伪装成已掌握知识。

## 提炼流程

1. 搜索 `02-概念/`，避免创建重复或近义笔记。
2. 选择清晰的名词短语标题；Topic Map 才使用宽泛主题名。
3. 保留用户表达中准确、有辨识度的理解，将其自然融入定义、直觉或机制解释；不要把对话原话单独堆成“我的理解”。
4. 读取并遵循 [领域标签注册表](../../docs/domain-tags.md)，选择一个主领域；只有真正跨领域时才增加第二个标签。
5. 读取并遵循 [正式笔记的实例与链接规范](../../docs/concept-note-writing.md)，为当前概念选择与领域真实工作方式匹配的应用案例，并检索可建立语义关系的现有笔记。
6. 以 [Concept Note 模板](assets/concept-note-template.md) 生成草稿，并删除所有说明性占位符。除非用户明确指定其他模板，不沿用旧模板中的“我的理解”“形式与例子”“理解验证”“来源与证据”等固定章节。
7. 在“概念与机制”的相应位置嵌入至少一个领域匹配的实际应用案例，包含具体场景、目标、条件、实施材料、可观察结果、概念映射和条件变化。软件知识按需使用实际代码、查询、配置或日志；硬件知识使用具体器件参数、连接或布局约束、测量与故障诊断；其他领域使用相应的演算、实验、决策、文本或设计案例。案例后必须抽象回一般机制，不能形成与正文割裂的附录。
8. “关系”中的每个目标都使用实际 Obsidian Wikilink，并写明关系类型和理由；模板里的纯文本槽位不能原样保留。不得制造无依据链接。
9. 展示完整目标路径、领域标签和草稿，等待用户明确确认；若需要新增宽泛领域标签，把注册表变更并入这次确认。
10. 确认后才写入 `02-概念/`，再更新掌握状态和相关 Topic Map；新建或更新的 Topic Map 统一只使用 YAML 标签 `map`，不添加 `domain/...`，导航目标继续遵循 Wikilink 规则。

不得直接覆盖已有 Concept Note。需要修改时先展示差异和理由，保留现有无关标签；增加、移除或替换领域标签必须出现在差异中。

`理解验证`、用户作答和晋升证据写入掌握状态或 Session Log，不进入 Concept Note。只有存在值得未来追溯的外部资料、标准、数据或实验记录时才增加“参考”，不为满足格式创建空章节，也不把本次对话当成来源。

展示草稿前自检：正文是否先完成基本阐述；案例是否嵌入并推动机制解释；是否使用该领域真实的应用材料；是否包含具体约束、过程、结果和条件变化；是否把构造案例冒充真实事件；关系目标是否写成可解析的 `[[...]]`；每条关系是否有语义理由。
