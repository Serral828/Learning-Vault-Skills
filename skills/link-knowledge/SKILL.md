# Link Knowledge

## 原则

- 开始前读取并遵循 [领域标签注册表](../../docs/domain-tags.md)。
- 开始前读取 [正式笔记的关系写法](../../docs/concept-note-writing.md#关系必须写成-obsidian-链接)，并按其中的 Wikilink 格式写入。
- 先搜索已有笔记，再提出关系。
- 新建或实质更新 Concept Note 时执行增量关系审计：既问“新笔记应该链接哪些旧笔记”，也问“哪些旧笔记现在应该显式链接这篇新笔记”。
- 不因为词语相似就建立链接。
- 不因为两篇笔记拥有相同领域标签就建立链接；标签用于宽泛分组，链接必须表达具体语义。
- 每条关系必须能用一句自然语言说明。
- 优先在正文中使用带上下文的 Markdown 链接，而不是堆砌“相关链接”。

## 常用关系

- `requires`：理解 A 需要先理解 B。
- `explains`：A 解释 B 的机制或原因。
- `applies-to`：A 被用于 B。
- `contrasts-with`：A 与 B 在某个维度形成对比。
- `causes`：A 在明确条件下导致 B。
- `evidence-for`：A 是 B 的证据。
- `generalizes`：A 是 B 的更一般形式。
- `addresses`：Concept Note 提供解决某个 Learning Quest 所需的机制、方法、边界或判断依据。
- `involves`：Learning Quest 在其知识路径或实际输出中涉及某个 Concept Note。

## 更新规则

- 宽泛主题进入 `03-主题地图/`，不要把 Topic Map 写成百科全书。
- 新 Concept Note 晋升后，读取并遵循 [Topic Map 创建与归属规范](../../docs/topic-map-writing.md)，必须为它处理至少一个最直接的上位 Topic Map。合适地图不存在时，提出创建带真实语义分组的最小地图；不得只报告未找到后结束。
- 一个概念可以属于多个 Topic Map，不通过深文件夹强制唯一归属。
- 更新已有 Topic Map 时，读取地图中全部链接目标，确定其主组织轴，把新概念放进有语义的分组并按依赖或领域自然顺序排列。若新增知识改变了结构，应同时提议移动、重命名分组或重排旧条目；禁止只向平铺的“已晋升概念”列表追加链接。
- 地图已有四个以上 Concept Note 仍未分类时，本次更新必须提出结构化重排。分类必须与主题内容匹配，不制造空分组、“其他”兜底或与现有知识无关的完整学科目录。
- Topic Map 更新提案必须展示组织轴、新概念的目标分组与组内位置、旧条目的结构差异和更新后的完整目录；写入后回读全部分组，验证没有丢失原有链接、重复收录、空分组或仍然平铺的笼统概念清单。
- 新建或实质更新 Concept Note 后，检索 `02-概念/` 中的关系候选。优先检查同一 Topic Map、同一 Quest、已有出链与反链、正文提到相关术语的笔记，以及在机制上可能把新概念作为输入、前置、组成或解释依据的旧笔记；不能只按文件名精确匹配。
- 对每个候选分别判断是否存在直接的 `requires`、`explains`、`applies-to`、`contrasts-with`、`causes`、`evidence-for` 或 `generalizes` 关系。共同标签、共同领域或同处一张 Topic Map 只能用于发现候选，不能作为建立关系的理由。
- 一旦确认 Concept Note 之间存在关系，必须准备和写入两侧显式 Wikilink。两侧可以使用不同关系类型和不同视角的理由，但必须语义一致。例如新“数据表示与特征向量”写“应用于：K 近邻分类（KNN）”，旧“K 近邻分类（KNN）”写“前置：数据表示与特征向量”。
- Concept Note 的 `## 关系` 固定放在 YAML 和一级标题之后，作为第一个二级章节。旧笔记缺少该章节时在一级标题后创建；章节位于文末或正文中部时，在提案差异中展示并将整个关系章节原样移动到一级标题后，再执行最小链接修改。存在“暂无已验证关系”时用真实关系替换；已经存在等价链接时不重复添加。章节移动不得丢失、改写或重复既有关系，也不得借此整篇重写旧笔记。
- 用户确认后回读每一对 Concept Note，验证两边都存在可解析链接。只写新侧、只写旧侧或依赖 Obsidian 自动反向链接面板，都视为未完成；被推迟的一侧必须交给 `learning-hub` 保存为包含文件对、两侧链接文本和理由的 `link-knowledge` 动作。
- 如果审计后没有直接关系，明确报告检查范围和不建立链接的理由；不要为了满足双向形式制造弱关系。
- `01-学习问题/` 与 `02-概念/` 的关系必须双向维护。Quest 使用 `## 涉及概念` 列出 `[[02-概念/<文件>|<标题>]] — <作用>`；Concept Note 的“关系”使用 `解决问题：[[01-学习问题/<文件>|<标题>]] — <作用>`。
- 新 Concept Note 来自当前 Quest，或已有 Concept Note 被当前 Quest 实际使用时，都要提出双向链接更新；不得只因标题相似链接，也不得只更新其中一个文件。
- 写入后回读两侧，验证目标文件真实存在、Wikilink 能解析、双方理由一致但不机械重复。缺少任一侧时视为未完成，并交给 `learning-hub` 保存 `link-knowledge` 待办。
- 新建或更新 Learning Quest 时，YAML `tags` 统一只保留 `quest`；新建或更新 Topic Map 时只保留 `map`；两者都不添加 `domain/...`。Concept Note 等其他正式知识仍按领域标签注册表分类。
- 提出新增或修改链接时，展示关系、理由、将写入的 `[[目标笔记]]` 和受影响文件，等待用户确认后再写入。
- 正文关系必须采用“关系类型 + Wikilink + 一句话理由”；不得写成纯文本目标、裸 URL 或只有链接没有语义的清单。存在同名歧义时使用带路径和别名的 Wikilink。
- 若 YAML 的 `prerequisites` 表达笔记关系，使用带引号的 Wikilink；写入后确认目标能够解析。没有可靠目标时明确写“暂无已验证关系”，不制造链接。
- 同时检查受影响正式笔记的标签是否缺失或明显不一致：Learning Quest 应恰好为 `quest`，Topic Map 应恰好为 `map`，其他正式知识检查领域标签。标签修正与链接修改分项展示，并在同一次确认后执行；不要把标签修正伪装成链接的附带副作用。
- 若需要新的宽泛领域标签，先在确认计划中说明边界与理由，用户确认后更新注册表再使用；不得创建窄标签或兜底标签。
