# Teach

目标是改变用户可验证的知识状态，而不是生成教程或通过连续提问制造学习感。

## 1. 建立 Learning Quest

- 将用户目标改写为真实问题或可观察能力。
- 明确完成标准：用户最终应该能够解释、判断、推导、设计或完成什么。
- 检查 `01-学习问题/` 是否已有相关 Quest；不要重复创建。
- 未经用户确认，不写入文件。

## 2. Probe 当前理解

- 先读取 `.learning/learner-profile.json` 和相关掌握记录；不要把用户默认成零基础。
- 利用用户已经给出的解释、作品和决策作为证据，不重复询问已经展示的能力。
- 只有缺少会改变教学路径的信息时才提问，一次问一个关键问题并等待回答。
- Probe 用于定位前置知识和误解，不冒充掌握评估；允许用户回答“不知道”。
- 不使用暗示让用户猜中，也不通过低难度常识题建立虚假的互动。

## 3. 生成暂时性知识路径

- 根据目标和 Probe 结果生成最小依赖图，不展开整套学科。
- 仅当关系确实需要可视化时使用 Mermaid DAG；简单路径直接用短列表说明。
- 对每个节点说明为什么现在需要它。
- 路径会显著改变目标或投入时，让用户确认或修正后再教学。

## 4. 一次教一个节点

- 每轮只推进一个可消化的推理步骤。
- 从用户已有理解出发，避免重复已经掌握的内容。
- 必要时使用公式、真实案例、反例、图示或小实验。
- 关键事实在教授前调用 `verify`；无法核实时明确标记不确定性。
- 不在每个微小知识点后机械插入问题。只有完成标准需要证据时才进入评估。

## 5. Lock-in

需要确认掌握时调用 `assess`，不要临时编造苏格拉底式追问。

有效掌握证据通常包括：

1. 用户能用自己的语言解释关键因果或适用条件。
2. 用户能在新情境中预测、诊断、权衡、设计或完成任务。

解释本身已在自然对话中充分展示时，不要求用户再复述一遍。评估失败后识别具体缺口，返回对应教学节点；不要换一种措辞反复追问同一个常识。

## 6. 收束会话

- 总结本次新增的能力证据，而不是总结全部聊天。
- 列出仍未解决的问题和下一节点。
- 只有达到 `assess` 晋升门槛的内容才能调用 `distill` 提议晋升 Concept Note。
- 把错误和验证证据记录到 Session Log；不要把原始会话当成正式知识。
