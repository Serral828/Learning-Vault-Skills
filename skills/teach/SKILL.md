# Teach

目标是改变用户可验证的知识状态，而不是生成教程或通过连续提问制造学习感。

## 1. 建立 Learning Quest

- 将用户目标改写为真实问题或可观察能力。
- 明确完成标准：用户最终应该能够解释、判断、推导、设计或完成什么。
- 调用 `learning-hub` 检查 `01-学习问题/` 和状态注册表；已有同一目标时复用稳定 Quest ID，不因新会话重复创建。
- 新目标由 `learning-hub` 提议 Quest ID、标题和持久化授权，再建立对应 Quest。
- 未经用户确认，不写入文件。

## 2. Probe 当前理解

- 先读取 `.learning/learner-profile.json` 和相关掌握记录；不要把用户默认成零基础。
- 利用用户已经给出的解释、作品和决策作为证据，不重复询问已经展示的能力。
- 只有缺少会改变教学路径的信息时才提问，一次问一个关键问题并等待回答。
- Probe 用于定位前置知识和误解，不冒充掌握评估；允许用户回答“不知道”。
- 不使用暗示让用户猜中，也不通过低难度常识题建立虚假的互动。

## 3. 生成暂时性知识路径

- 根据目标和 Probe 结果生成最小依赖图，不展开整套学科。
- 仅当关系确实需要可视化时使用 Mermaid DAG；简单路径直接用短列表说明。
- 每个节点必须是一个可独立评估的能力单元，并在路径中同时写明：为什么现在需要它、怎样算完成、准备使用哪类新情境取得证据。无法单独评估的微小知识点并入相邻节点。
- 路径还必须定义一个覆盖全部必需节点的实际应用输出，以及针对该输出和 Quest 完成标准的综合评估。节点练习不能代替最终输出。
- 路径会显著改变目标或投入时，让用户确认或修正后再教学。

## 4. 一次教一个节点

- 每轮只推进一个可消化的推理步骤。
- 从用户已有理解出发，避免重复已经掌握的内容。
- 必要时使用公式、具体案例、反例、图示或小实验。
- 关键事实在教授前调用 `verify`；无法核实时明确标记不确定性。
- 不在每句话或微小知识点后机械插入问题。讲解和教师示例结束后先进入“疑问澄清”；用户明确要求测试时最多评估一次，用户要求继续时直接放行。

### 具体示例门槛

解释一个新的机制、因果关系、边界或抽象术语时，除非用户已经提供并正确使用了一个具体实例，或明确要求只给简短定义，否则在进入下一节点前给出至少一个**可推演的实例**。只提到一个场景、对象或类比，不算完成举例。

一个合格实例应让用户看见概念如何作用，通常包含：

1. **具体输入或现象**：给出实际字符串、数值、样本、日志、操作或可观察差异；假设数据要明确标注为假设。
2. **中间机制**：逐步指出系统、模型或人的判断依据发生了什么，而不是直接跳到结论。
3. **可观察结果**：说明最终预测、行为、输出或失败表现。
4. **条件变化**：改变一个关键条件，展示哪些规律仍成立、哪些偶然线索会失效。
5. **概念映射**：用简短对应关系指出实例中的每个部分分别代表哪个抽象概念。

需要比较时优先使用最小对照表、短执行轨迹或“原条件 → 变化 → 结果”，不要用更多抽象描述代替实例。优先取材于用户正在做的项目；没有真实材料时构造最小但完整的假设情境，不把虚构数字说成事实。

实例载体必须匹配领域的真实应用方式：软件知识优先展示实际代码、配置、请求响应、数据或日志；硬件知识展示具体器件参数、连接或布局约束、信号与测量、故障现象和工程取舍；数学与统计完成带数值的演算；自然科学展示实验或观察；商业、社会科学、人文、设计、健康和教育使用各自真实的决策材料、文本证据、作品约束、观察指标或实践案例。代码只是软件类实例的一种常见载体，不是所有领域的统一要求。

低质量：

> 训练数据里混着巧合，比如一批垃圾邮件恰好使用固定排版，模型可能把排版记下来。

这只是给巧合起了一个名字，没有展示模型学到了什么，以及数据变化后怎样失败。

合格：

> 假设训练集里有 100 封垃圾邮件，其中 90 封都在底部放同一种二维码；100 封正常邮件都没有。模型发现“出现这种二维码”几乎总能猜对，于是主要依赖它，而没有学会识别催促转账、伪造身份等内容特征。上线后，一家正常商店的促销邮件也使用了这种二维码，模型把它误判成垃圾邮件；骗子换成纯文本后，模型又漏判。这里，催促转账等内容模式是更可能跨数据保持的信号，特定二维码是训练集中的偶然线索，高训练准确率但新数据误判是过拟合的可观察结果。

不要连续罗列多个只有一句话的浅例子；一个能够逐步推演、包含条件变化的实例通常更有效。类比只能辅助直觉，不能代替真实机制。完成实例讲解后先进入疑问澄清窗口；只有用户明确要求测试时才进入 `assess`。

### 节点边界、疑问窗口与评估

每个学习节点按以下顺序推进：

1. **教学中**：解释机制并给出领域匹配的可推演实例。
2. **疑问澄清**：讲解和实例结束后先停在本节点，明确告诉用户“现在先不评估”，并由 Agent 主动询问用户是否还有疑问、是否准备进入评估。不得只是等待用户自己提出，也不得在同一条消息中附上评估题。
3. **待评估或直接放行**：不存在未解决的阻塞暂存依赖时，用户明确说“开始评估”“可以测试”才调用 `assess` 出一个核心任务；用户说“下一步”“可以通过”“没问题”“我懂了”“继续”时按用户直接放行规则记为 `validated`，不再出题。`waiting_on_deferred` 节点不适用直接放行。
4. **评估完成**：实际作答达到预设等级时记为 `validated`；未达到时记为 `assessed_with_gaps` 并记录缺口。两种情况都进入下一节点，不补测。
5. **节点完成**：所有必需节点分别完成一次评估或被用户直接放行后，进入实际应用输出阶段；单个节点此时仍不能提前 Distill。

疑问澄清阶段遵循以下规则：

- 用户提出问题时，继续留在当前节点，直接回答问题；必要时补充另一个可推演实例、对照、代码、工程案例或反例。
- 用户的问题是学习请求，不是评估答案。不得对问题判级、记录为缺口或以“先回答评估题”为由推迟解释。
- 首次讲解结束以及每次回答完疑问后，都必须由 Agent 主动询问：“这一节点还有哪里需要解释？如果没有，是否现在进入评估？也可以说‘下一步’直接继续。”可以自然改写，但必须同时保留“继续提问、进入评估、直接继续”三个入口。
- 询问是否进入评估只是阶段确认，不是评估题。用户选择进入评估后，下一条消息才调用 `assess` 出题。
- 用户只说“还有点不懂”但没有指出位置时，可以询问一个简短的定位问题；这属于澄清，不属于评估追问。
- 不使用单独的“懂了吗？”作为逼迫式检查，也不能省略“是否进入评估”的主动询问。

### 用户主动暂存概念

Teach 必须先正常解释节点知识和相关概念，不得根据对用户水平的猜测自动降低概念深度、创建黑箱模型或暂存概念。用户说“没听懂”“为什么”“再举个例子”时继续执行疑问澄清。

只有用户明确说“现阶段无法理解，先暂存”“以后再学”，或主动调用 `/skill:defer-concept <概念>` 时，才暂停当前教学并调用 `defer-concept`：

1. 传递当前 Quest、节点、完成标准、概念为何被引入、已经讲过的机制和实例、已知卡点及返回位置。
2. 由 `defer-concept` 根据“拿掉该概念后，当前节点能否达到原完成标准”记录本次来源为 `blocking` 或 `supporting`，并向用户说明理由和后果。
3. `blocking` 时当前节点进入 `waiting_on_deferred`，不得评估或直接放行；继续其他不依赖它的节点，没有可继续节点时暂停 Quest。
4. `supporting` 时返回当前节点继续教学，后续评估明确排除该概念。

暂存是用户选择的学习调度，不是答错、知识缺口或掌握证据。Teach 不得把暂存内容写入 `gaps`，也不得自动为它安排简化讲解、评估、复习或 Concept Note。

### 疑问解答的沉淀

用户在节点中提出的实质性疑问及其解答属于教学成果，不能只留在聊天里。每次完成澄清后维护当前节点的 `clarificationInsights`：

- `question`：用户真正困惑的机制、边界、区别或应用问题，用简洁语义概括，不机械复制整段原话。
- `resolution`：最终讲清的关键解释，包括必要条件、因果链或判断方法。
- `exampleOrBoundary`：为解决疑问新增的例子、反例、代码、工程条件或适用边界；没有则省略。
- `noteUse`：建议在 Concept Note 中进入“概念与机制”“适用边界与常见误区”“实际应用案例”或“关系”的位置。

只记录对理解概念有长期价值的澄清，不记录寒暄、流程选择或纯粹的界面问题。进入综合评估和 Distill 时必须把这些记录一并传递；不得因为用户直接放行评估而丢弃此前的疑问解答。

用户已经在自然对话中主动完成了等价的新情境应用时，仍调用 `assess` 对现有回答判级，但不重复出题；明确告诉用户“刚才的回答已经作为本节点的评估证据”。没有提问、也没有自然证据时，不得把节点标为已验证。

如果用户在评估时表示“可以通过”“可以了”“我懂了”“下一步”“继续”“这部分过了”或同义意思，并且当前节点不存在未解决的阻塞暂存依赖，按 `assess` 的“用户直接放行”规则立即把当前节点标为 `validated`，不再追问，也不记录缺口。用户的推进指令优先于证据分析，但不能绕过 `waiting_on_deferred`。

每个规划节点都必须有一次独立的 `assess` 事件和独立证据记录，每次只判定一个节点。用户的一次自然回答可以为其他节点提供线索，但不能把多个节点合并成一次评估来省略步骤；如果两个内容无法独立判断，就应在规划阶段把它们定义成一个节点。任何节点评估都不能替代全部节点之后的实际应用输出和综合评估。

评估未达到目标等级时，简短纠正暴露出的具体缺口并记录为 `assessed_with_gaps`，随后继续既定路径；不得自动换题补测或要求用户重新作答。用户明确希望巩固时，再把该缺口交给 `review` 或另建教学节点。

## 5. 可运行代码的执行交接

只要准备给出需要用户复制到本地运行、查阅或修改的代码块，就不要把复制粘贴当作默认交付方式。改为创建完整的练习工作区并打开编辑器。

### 读取配置

先读取 `.learning/tooling.json`：

- `learningLabsRoot`：Vault 内默认隔离的代码实验根目录，通常是 `98-代码实验/`。
- `editor.command`：用于打开工作区的编辑器命令。
- `handoff.openAfterWrite`：写入成功后是否打开编辑器。
- `handoff.runAfterWrite`：必须保持为 `false`，除非用户在当前请求中明确要求运行。

配置不存在或目标目录不明确时只询问一次，不猜测路径。不要把个人绝对路径写入可复用 Skill。

`98-代码实验/` 不参与普通检索，但本 Skill 在已经确定具体实验目录后可以显式访问该目录。不要扫描其他实验来寻找“可能相关”的代码；只有用户明确要求继续某个既有实验时才读取对应目录。

### 创建练习工作区

1. 根据当前知识点或实验目的生成简短、稳定的 kebab-case 目录名。
2. 同一实验继续迭代时复用原目录；若名称冲突但内容属于另一实验，使用有意义的后缀。未经确认不得覆盖已有文件。
3. 创建能够直接查阅和运行的完整材料，而不是强制挖空核心代码。学习目标是方法、行为或取舍时，代码可以是完整实现。
4. 至少写入：
   - 可运行的源代码文件；
   - `README.md`，说明学习目标、方法思路、文件作用、前置条件、运行命令、关键参数、建议观察点和可尝试的修改；
   - 项目实际需要的依赖声明；
   - 涉及环境变量时创建 `.env.example` 和 `.gitignore`，只写变量名和占位符，绝不写入真实密钥。
5. 代码和说明全部写入成功后，执行配置中的编辑器命令打开整个实验目录，例如 `code <lab-directory>`。
6. 只完成“写入并打开”。不要自动安装依赖、启动服务或运行代码；这些动作由用户决定。

完成后在聊天中只说明实验路径、文件清单、建议从哪里开始以及运行命令。除非用户要求，不再重复粘贴已经写入文件的完整代码。

### 能力与权限边界

执行交接需要 Agent 具备目标目录写入与运行编辑器命令的权限。当前模式缺少权限时，明确说明需要切换到允许文件写入与 Shell 的模式；不要悄悄退化成长代码块让用户复制。

## 6. Lock-in

每个规划节点完成教学实例后先进入疑问澄清窗口，不得立即调用 `assess`。用户明确要求开始评估后才调用 `assess`，并且不要由 `teach` 临时编造苏格拉底式追问；用户明确要求下一步时则按直接放行规则完成节点。

已经提出评估问题后，用户用“下一步”“可以通过”等方式明确要求推进，就直接结束该次 `assess` 并进入下一阶段；不得把这类表达判成“没有作答”或 `assessed_with_gaps`。

有效掌握证据通常包括：

1. 用户能用自己的语言解释关键因果或适用条件。
2. 用户能在新情境中预测、诊断、权衡、设计或完成任务。

解释本身已在自然对话中充分展示时，不要求用户再复述一遍；评估只执行一次。证据不足时识别并记录具体缺口，但不返回原节点补测，也不要换一种措辞反复追问同一个常识。

## 7. 实际应用输出与综合评估

所有必需节点分别完成一次评估后，不立即调用 `distill`。先要求用户完成一个整合当前 Quest 的实际应用输出：

- 软件、Web、AI、数据：可运行程序、查询、配置、调试结论、模型实验或带结果的技术方案；
- 硬件、电子、嵌入式：设计方案、参数计算、连接或布局决策、测量分析、故障诊断与验证步骤；
- 数学、统计、自然科学：完整推导、数据分析、实验设计、预测与误差解释；
- 商业、社会科学、人文、设计、健康和教育：带真实约束的决策、案例分析、方案、作品或干预设计。

输出必须由用户作出并能观察到其推理或结果。Agent 可以提供题目、数据、脚手架和反馈，但不能替用户完成后再把自己的产物当成用户证据。用户已有真实项目或作品覆盖完成标准时，直接使用它，不要求重复造一个练习项目。

取得实际应用输出后，再次调用 `assess`，明确使用“综合评估”模式：

1. 对照 Quest 完成标准检查输出是否联合使用了全部必要节点，而不是把节点评分简单求和。
2. 检查用户能否解释关键决策、诊断失败、处理一个变化条件或指出适用边界。
3. 输出整体结论、各节点在成果中的证据、仍存在的缺口，以及哪些核心命题具备 Distill 条件。
4. 综合评估结果为 `passed` 或 `completed_with_gaps`；后者记录具体缺口，但不要求补做输出或复评。
5. 综合评估完成后进入 Distill，把准确的知识内容整理成笔记；掌握不足的部分保留在学习状态中，不能因为生成笔记而改写为已掌握。

综合评估过程中用户明确说“可以通过”“下一步”“继续生成笔记”等推进表达时，立即记为 `passed`、清空 `gaps` 并进入 Distill，不再追加问题。

## 8. 跨会话恢复

Quest ID、跨会话检查点、多个 Quest 和未来动作都由 `learning-hub` 管理。恢复已有 Quest 时先由它解析 ID 和状态，再从对应节点继续；本 Skill 不直接重建或覆盖 `.learning/learning-progress.json`。

用户表示暂停、没时间或准备结束时，把当前节点、`clarificationInsights`、能力证据、缺口和完成状态交回 `learning-hub`。完整 Session Log 可以延期，但不能因此丢失恢复所需状态或已经讲清的重要疑问。

## 9. 收束会话

正常收束包括完成当前路径、开始总结或给出后续选项；在这些动作之前按顺序执行一次收束审计：

1. 检查每个必需节点。仍在疑问澄清阶段时先等待用户提问、要求评估或直接放行，不能自动出题；只有用户明确选择评估后才调用 `assess`。
   - 如果节点存在未解决的 `blocking` 暂存依赖，保留 `waiting_on_deferred` 并交给 `learning-hub` 保存返回路径；不得把该节点直接放入评估或通过。
2. 全部节点各完成一次评估后，检查用户是否已经完成覆盖整个 Quest 的实际应用输出；没有时进入输出任务，不能把节点练习直接汇总成 Distill 证据。
3. 输出完成后再次调用 `assess` 做一次综合评估；无论结果是 `passed` 还是 `completed_with_gaps`，评估到此结束，不安排补测。
4. 综合评估完成后，对可准确整理的知识节点主动调用 `distill`，直接展示候选 Concept Note 和目标路径，请用户确认是否写入；草稿必须按正式笔记规范用 `==...==` 标出重要概念的引入或关键阐述，用 `**...**` 标出其他重要结论。不要等用户另行提醒或手工调用。
5. 用户对草稿的写入确认只代表授权落盘，不是掌握证据。不得用“先给候选稿让你审阅”替代节点评估、实际应用输出或综合评估。
6. 完成必要的 Distill 提案后，再总结本次新增的能力证据，并把节点状态、疑问解答摘要、应用输出、综合评估、Distill 状态、缺口和可复习内容交给 `learning-hub`。
7. 由 `learning-hub` 给出最多两个可在未来执行的动作；不要用后续选项掩盖尚未完成的评估、输出或提炼。

只有用户明确表示现在必须停止、没时间继续时，才可以暂停这条顺序：分别保存为“待首次节点评估”“待实际应用输出”“待首次综合评估”或“待 Distill”。已经评估但有缺口的节点不创建补测待办。

禁止在用户事后追问“为什么没有笔记”时，才给出“先补测还是先看候选稿”的二选一。正确流程是每个节点主动评估一次，全部节点评估后完成实际应用输出和一次综合评估，最后主动提议 Distill；评估中记录的缺口不阻止本次笔记整理。

需要完整复盘时把错误和验证证据记录到 Session Log。不要把原始会话当成正式知识。
