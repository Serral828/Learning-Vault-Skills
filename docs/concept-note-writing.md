# 正式笔记的实例与链接规范

本规范适用于 Agent 新建或更新的 Concept Note，以及以解释机制为主的方法、实践笔记。目标是让笔记能够独立把知识讲清楚、让应用案例参与解释，并让关系真正进入 Obsidian 的链接图谱。

## 正式知识不是学习过程记录

Concept Note 面向未来再次理解和使用知识，不复刻这次对话的教学流程。默认不设置以下章节：

- `我的理解`：用户在对话中的原话不是独立正文。保留其中准确、有辨识度的表达，把它自然融入定义、直觉或机制解释。
- `理解验证`：能否复述、是否通过评估、容易犯什么错属于掌握证据，写入 `.learning/` 或 `90-学习会话/`；概念本身的常见误区可以进入“适用边界与常见误区”。
- `来源与证据`：不把本地代码路径、聊天过程或“本次已验证”当作默认结尾。只有存在值得未来追溯的外部资料、标准、论文、数据或实验记录时，才添加简短的“参考”章节或行内链接。

正式笔记首先要回答：它是什么、为什么成立或如何运作、在实际情境中怎样表现、何时适用或失效，以及它和已有知识是什么关系。

## 默认叙事结构

使用下列骨架，但根据概念自然增减三级标题，不机械填表：

```markdown
# <概念标题>

## 核心命题
<一到三句话给出可判断的结论，避免在这里展开全部细节。>

## 概念与机制
<先给基本定义和必要术语，再按因果或步骤连贯解释。>

### <与内容相关的小标题>
<在讲到机制实际发生的位置嵌入领域应用案例、代码、参数、演算、材料或观察结果。>

<从案例抽象回一般规律，说明为什么这个例子能够支持前面的解释。>

## 适用边界与常见误区
<说明成立条件、失败模式、容易混淆的相邻概念。没有实质内容时可以省略。>

## 关系
- 前置：[[目标笔记]] — <理由>
- 解释：[[目标笔记]] — <理由>
```

只有确有可追溯资料时，才在最后增加：

```markdown
## 参考

- [[实验记录或来源笔记]]
- [外部资料标题](URL)
```

标题顺序服务于论证，不要求案例永远拥有独立的“形式与例子”章节。若案例正好解释某一步机制，就把它放在该步骤之后；若案例贯穿全文，可用案例作为主线，再逐步抽象出一般规律。

## 每篇笔记都要有领域匹配的实际应用

每篇解释型正式笔记至少提供一个能够推演的实际应用案例。案例必须嵌入相关知识点的阐述，而不是在正文结束后附上一块彼此割裂的“例子”。代码只是软件知识常见的案例载体；硬件、数学、商业、人文等领域必须选择各自真实的应用形态，不能为了统一格式强塞代码。

一个合格案例通常包含：

1. **具体对象与场景**：系统、设备、数据、组织、文本、事件或实验对象是什么。
2. **实际目标**：要实现、判断、解释、诊断或改进什么。
3. **条件与约束**：给出必要的数值、环境、资源、规则或背景；假设内容明确标注为假设案例。
4. **实施过程或实际材料**：展示代码、电路参数、测量结果、演算、决策资料、原始文本等该领域真正会使用的材料。
5. **可观察结果**：说明输出、测量、结论、取舍或失败表现。
6. **概念映射**：指出案例中的各部分分别对应抽象概念的什么角色。
7. **条件变化或边界**：改变一个关键条件，说明结果如何变化，以及概念何时不再适用。

只写“这个概念可用于垃圾邮件分类”“它常见于电源设计”等一句话场景不算实际应用案例。案例可以来自有来源的真实项目，也可以是数值和约束完整的工程化假设；不得把构造案例冒充真实事件。案例结束后要明确抽象回知识点：这个结果说明了什么机制、哪些细节只是情境参数。

## 按领域选择案例载体

以下是选择依据，不是封闭分类：

| 领域 | 优先使用的实际材料 |
| --- | --- |
| 软件、Web、AI、数据 | 最小可运行代码、SQL、配置、API 请求与响应、真实形状的数据样本、日志或执行轨迹 |
| 硬件、电子、嵌入式 | 具体器件与参数、供电和负载条件、连接关系、信号时序、测量数据、故障现象、设计取舍；需要固件时再附实际代码 |
| 数学、统计 | 带具体数值的完整演算、数据表、模型假设、计算步骤、结果与敏感性变化 |
| 自然科学 | 实验或观察条件、变量控制、测量方法、数据、预测和误差来源 |
| 商业、社会科学 | 具体组织或决策者、目标、约束、数据、利益相关者、方案取舍和结果；虚构案例要标明 |
| 人文、历史、法律 | 具体文本、史料、事件或案例事实，结合上下文、证据来源和不同解释进行分析 |
| 设计、艺术 | 明确的用户或受众、设计任务、约束、方案、原型或作品细节，以及评价和迭代依据 |
| 健康、教育 | 具体人群或学习者、目标、条件、干预过程、观察指标和限制；高风险结论必须有可靠来源 |

### 软件类案例中的代码标准

当代码、查询或配置是该知识在实际工作中的自然载体时：

- 使用带语言标识的 fenced code block，给出最小但完整的实际实现，不用省略核心逻辑的 `...` 冒充示例。
- 紧跟输入、预期或实测输出，并解释关键语句如何体现概念。
- 至少改变一个参数、输入或约束，展示结果为什么变化。
- 没有实际执行时写“预期输出”，不得假装已经验证。

若 HTTP 报文、SQL、配置差异或执行日志比程序代码更能体现实际应用，就使用这些材料，不为满足“代码块”形式而选择错误载体。

### 硬件类案例中的工程标准

硬件案例至少要让读者看见“设计条件 → 工程选择 → 可测结果”。例如应给出供电电压、负载或频率、器件参数、关键连接或布局约束、示波器或万用表会观察到什么，以及条件变化后可能出现的故障。只说“加一个电容可以滤波”不够；需要说明在哪个节点、面对什么噪声、为何选择该参数以及如何验证。

较长、需要多个文件或依赖的软件实验仍放入 `98-代码实验/`；复杂硬件项目可链接 `05-实践与产出/` 中的设计或实验记录。Concept Note 保留足以独立解释机制的最小应用材料。

## 关系必须写成 Obsidian 链接

创建草稿前先搜索现有正式知识。关系部分中的目标必须使用 Obsidian Wikilink，不写成无法点击的纯文本名称：

```markdown
## 关系

- 前置：[[监督学习中的训练]] — 需要先理解训练数据如何影响模型。
- 解释：[[泛化与过拟合]] — 本概念解释了模型为何会记住训练噪声。
- 应用于：[[垃圾邮件分类]] — 可用于判断分类器在新邮件上的表现。
- 对比：[[训练误差]] — 两者分别反映已见数据与未见数据上的表现。
```

规则：

- 每条关系包含“关系类型 + `[[目标笔记]]` + 一句话理由”，不能只堆链接。
- 链接现有笔记时使用实际文件名；存在同名歧义时使用 `[[相对路径/文件名|显示名称]]`。
- 不把 `.md` 扩展名写进 Wikilink。
- 若 YAML 的 `prerequisites` 保存笔记关系，也使用带引号的 Wikilink，例如 `- "[[监督学习中的训练]]"`。
- 只写能够说明语义的关系。没有可靠目标时写“暂无已验证关系”，不要用纯文本占位，也不要制造虚假或无意义链接。
- Topic Map 中的导航条目同样使用 Wikilink，并在需要时用短语说明为什么值得进入该笔记。

Obsidian 会从 Wikilink 建立图谱边；关系类型和理由则让链接在离开图谱后仍然可理解。
