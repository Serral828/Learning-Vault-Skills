# 学习流程规则

这是 Teach 流水线的**唯一规则来源**：节点生命周期、疑问澄清窗口、直接放行、评估收束、阻塞暂存门槛、综合评估与 Distill 门槛。`teach`、`assess`、`distill`、`learning-hub`、`defer-concept` 只描述各自的职责，遇到这些规则时引用本文，不再复述。修改规则只改这里。

字段结构和文件写入责任见 [learning-hub 状态模型](../skills/learning-hub/references/state-model.md)，本文只定义流程行为。

## 1. 各 Skill 的职责

| Skill | 在流程中做什么 | 不做什么 |
|---|---|---|
| `teach` | 教学、疑问澄清、组织应用输出、收束审计 | 不自行编造评估追问，不写 `learning-progress.json` |
| `assess` | 每次判定一个节点或一次综合评估，返回证据记录 | 不在澄清窗口内出题，不安排补测 |
| `distill` | 综合评估后提炼候选 Concept Note | 不把草稿确认当作掌握证据 |
| `defer-concept` | 记录和恢复暂存概念，判定 `blocking`/`supporting` | 不评估、不安排简化讲解 |
| `learning-hub` | 保存 Quest 状态、恢复与路由 | 不替代上述任何一个 |

## 2. 节点状态

状态名以 [状态模型](../skills/learning-hub/references/state-model.md) 为准，本表只说明流程含义。

| 状态 | 含义 |
|---|---|
| `teaching` | 正在讲解 |
| `clarifying` | 已讲解并给出实例，处于疑问澄清窗口 |
| `awaiting_assessment` | 用户已明确要求评估，尚未完成 |
| `validated` | 本节点的一次评估已完成且达到目标等级，或用户直接放行 |
| `assessed_with_gaps` | 本节点的一次评估已完成但未达到目标等级，缺口已记录 |
| `waiting_on_deferred` | 存在未解决的 `blocking` 暂存依赖 |

`validated` 与 `assessed_with_gaps` 都表示本节点已完成，可以进入下一节点。

## 3. 节点生命周期

1. **教学中**：解释机制，并按 [具体示例标准](../skills/teach/references/example-standard.md) 给出领域匹配的可推演实例。
2. **疑问澄清**：讲解和实例结束后停在本节点，明确告知“现在先不评估”，由 Agent 主动询问下一步。不得在同一条消息中附评估题。
3. **评估或放行**：无未解决的 `blocking` 依赖时，
   - 用户明确要求“开始评估”“可以测试”才调用 `assess`，只出一个核心任务；
   - 用户说“下一步”“可以通过”等，按第 5 节直接放行。
4. **评估完成**：见第 6 节。
5. **可选保存评估摘录**：见第 8 节。
6. **节点完成**：所有必需节点各完成一次评估或被放行后，进入第 9 节。单个节点此时不能提前 Distill。

每个规划节点必须有一次独立的 `assess` 事件和独立证据记录，一次只判定一个节点。用户的一次自然回答可以给其他节点提供线索，但不能合并成一次评估；无法独立判断的内容应在规划阶段合并为一个节点。

## 4. 疑问澄清窗口

- 用户提问时留在当前节点直接回答，必要时补充实例、对照、代码、工程案例或反例。
- 用户的问题是学习请求，不是评估答案：不判级、不记缺口、不以“先回答评估题”推迟解释。例如“为什么要归一化”“这个例子没看懂”“再举个例子”“这和上一概念有什么区别”。
- 首次讲解结束后，以及每次回答完疑问后，Agent 必须主动询问。措辞可自然改写，但要同时保留三个入口：**继续提问、进入评估、直接继续**。示例：“这一节点还有哪里需要解释？如果没有，是否现在进入评估？也可以说‘下一步’直接继续。”
- 询问是否进入评估只是阶段确认，不是评估题；用户选择评估后，下一条消息才出题。
- 用户只说“还有点不懂”而没指出位置时，可以问一个简短的定位问题，这属于澄清。
- 不使用单独的“懂了吗？”作为检查，也不能省略“是否进入评估”的询问。
- 用户已在自然对话中完成等价的新情境应用时，仍调用 `assess` 判级但不重复出题，并告诉用户“刚才的回答已经作为本节点的评估证据”。既没有提问也没有自然证据时，不得把节点标为已验证。

## 5. 直接放行

适用条件：当前节点没有未解决的 `blocking` 暂存依赖。用户在澄清窗口（未调用 `assess`）或评估过程中表达推进意图，都适用。

用户明确表达“可以通过”“可以了”“我懂了”“下一步”“继续”“这部分过了”“跳过这个问题”或语义等价的推进意图时，视为要求结束本次评估，而不是需要分析的答题内容：

- 节点模式：立即记为 `validated`，`gaps` 为空，证据等级按该节点要求等级记录。
- 综合模式：立即记为 `passed`，`distillReady: true`，`gaps` 为空，进入 Distill。
- 不再追问、纠正，也不用“你确定吗”“请先解释理由”或换题继续评估。
- 语境清楚表示通过或前进即可，不要求固定口令；孤立且语义不明的“可以”按正常上下文理解。
- 已提出评估问题后，用户以这类方式推进，直接结束该次评估，不得判成“没有作答”或 `assessed_with_gaps`。
- 直接放行没有可摘录的问答，不生成评估摘录候选。

## 6. 评估收束与不补测

- 节点检查通常达到证据等级 `2` 记为 `validated`，未达到记为 `assessed_with_gaps` 并记录具体缺口。两者都进入下一节点。
- 未达到时只给出针对具体缺口的简短纠正，**不换题补测，不要求用户重新作答**，也不为缺口创建补测待办。
- 用户明确要求巩固时，才把缺口交给 `review` 或另建教学节点。
- 综合评估同理：`passed` 或 `completed_with_gaps` 后评估结束，不补做输出、不复评。
- 证据不足时记录缺口，但不返回原节点，也不换措辞反复追问同一个常识。
- 解释已在自然对话中充分展示时，不要求用户再复述。
- 生成 Concept Note 不等于把缺口改写为已掌握；缺口留在掌握状态中。

## 7. 阻塞暂存门槛

- 只有用户明确说“现阶段无法理解，先暂存”“以后再学”，或调用 `/skill:defer-concept <概念>` 时才暂存。`teach` 不得根据对用户水平的猜测自动暂存、降低概念深度或创建黑箱模型；“没听懂”“为什么”按第 4 节继续澄清。
- `blocking`：当前节点进入 `waiting_on_deferred`，**禁止评估、直接放行、实际应用汇总和 Distill**。继续其他不依赖它的节点，没有可继续节点时暂停 Quest。用户说“下一步”“可以通过”也不能绕过。
- `supporting`：返回当前节点继续教学；后续评估必须把该概念排除在题目、评分标准和隐藏前置之外，不生成 evidenceLevel、gaps 或 mastery。
- 暂存是学习调度，不是答错或缺口；不得写入 `gaps`，也不得自动安排简化讲解、评估、复习或 Concept Note。

## 8. 澄清沉淀与评估摘录

两类记录分开保存。

- `clarificationInsights`：记录“用户问了什么、最终怎样讲清”。字段为 `question`、`resolution`、`exampleOrBoundary`（可省略）、`noteUse`（建议放入“概念与机制”“适用边界与常见误区”“实际应用案例”或“关系”）。只记录对理解概念有长期价值的澄清，不记录寒暄、流程选择或界面问题。综合评估和 Distill 时必须传递，不因用户直接放行评估而丢弃。
- `assessmentNoteExcerpts`：只记录用户**明确同意**纳入笔记的评估引用块。每项包含标题、情境摘要、回答要点、结论或校正、建议插入位置和 `approved`/`included` 状态。

摘录候选由 `assess` 生成并按其规则展示。用户拒绝、说“不记录”或“下一步”时丢弃，不记为缺口或待办。同意只授权进入最终草稿；正式文件仍只能在综合评估完成、Distill 展示完整草稿并得到最终确认后写入。

## 9. 应用输出与综合评估

所有必需节点各完成一次评估后，不立即 Distill，先要求用户完成一个整合当前 Quest 的实际应用输出，载体按领域选择（见 `teach` 第 6 节）。

- 输出必须由用户作出，并能观察到其推理或结果。Agent 可提供题目、数据、脚手架和反馈，但不得替用户完成再当作用户证据。用户已有真实项目或作品覆盖完成标准时直接使用。
- 取得输出后调用 `assess` 的 `mode: comprehensive`，判定方式见 `assess`。

## 10. Distill 门槛与收束顺序

正式 Concept Note 必须同时满足：全部必需节点各评估一次（`validated` 或 `assessed_with_gaps`）、实际应用输出已完成、一次综合评估已结束（`passed` 或 `completed_with_gaps`），并且关键事实有来源或标注为个人推断、边界小且有唯一核心命题。未满足时内容保留在 `90-学习会话/`。

用户审阅或确认草稿只能授权修改或写入，不能替代节点评估、应用输出或综合评估。

收束审计按此顺序执行，每一步只做一次：

1. 检查每个必需节点。仍在澄清阶段时等待用户提问、要求评估或放行，不自动出题；存在 `blocking` 依赖的节点保留 `waiting_on_deferred` 并交给 `learning-hub`。
2. 全部节点完成后，检查是否已有应用输出；没有则进入输出任务。
3. 输出完成后做一次综合评估。
4. 综合评估完成后主动调用 `distill`，同时传递已批准的 `assessmentNoteExcerpts` 和 `clarificationInsights`。用户不需要另行发出 `/skill:distill`。
5. 提炼结束后，把节点状态、澄清摘要、摘录及写入状态、应用输出、综合评估、Distill 状态、缺口和可复习内容交给 `learning-hub`，由它给出最多两个未来动作。

禁止在用户事后追问“为什么没有笔记”时才给出“先补测还是先看候选稿”的二选一。

只有用户明确表示现在必须停止时，才可暂停这条顺序，并分别保存为“待首次节点评估”“待实际应用输出”“待首次综合评估”或“待 Distill”。已评估但有缺口的节点不创建补测待办。用户没时间查看草稿时，把该节点交给 `learning-hub` 保存为待执行 `distill` 动作，下次恢复先展示草稿，不重新教授或补测。用户明确拒绝晋升时记录为 `declined`，证据不变时不反复推销。
